# Plan and implementation review

Date: 2026-10-25. Requirements: version 0.5. Configurator baseline: `42bad4d10a59e77297dc1e2a0e80eff79164053b`, `desktop-dev`, including the uncommitted profile/model/key-picker changes present during inspection. Firmware reference: `dvino/ak820` tag `v0.6.0-beta.1`, commit `bef20f89d3da01d770767919bc7c8fc3c3a1a808`.

This review covers the plan, requirements, current native source, existing AK820 test cases and development workflow. The architecture reviewer inspected source and tests without running a competing build. After the final Auto Shift and Mouse Keys tests and the invalid-input guard were added, the lead ran `cargo test --locked --all-targets`: **1549 passed, 0 failed, 14 ignored**, 260.88 s. Ignored cases are not passes. Prior executions and their boundaries remain recorded in [REVIEW.md](REVIEW.md). No physical keyboard was operated. This is not an exhaustive review of inherited Entropy functionality or independent approval of the documentation authored here.

## Plan corrections

The plan and requirements now use the nine whole beta.1 profiles and native-first sequence. They explicitly include exact image contracts, source-aware keycodes, schema03 typed editors, complete firmware-compatible backups, migration and transitions, companion installer/OEM operation models, six OS/CPU targets and maximum completion without a keyboard. The former alpha.3 editor milestone remains identified as a limited implementation. No hardware or release approval was added.

The beta.1 firmware matrix and descriptions are design inputs. Its standalone installer includes only `work`; catalog presence and firmware offline qualification do not enable companion writes. The firmware handoff contains older desktop sequencing/platform wording; current configurator requirements govern the expanded six-target scope and native-first ordering.

## Implementation and coverage gaps

1. **Beta.1 has no operational editor contract yet** (AKW-003, 012, 015, 024). **Release blocker for beta editing; offline implementation.** `src/ak820.rs::{parse_manifest,recognize_image,CAPABILITIES}` accepts only schema02 and the pinned alpha.3 CODE hash. `src/hid_ak820.rs::verify_ak820_firmware` enforces that pin. `src/ui/ak820_connection.rs::load_verified_ak820` requires the alpha.3 capacities and disables extension controls. `src/ak820_beta1_profiles.rs::{MatrixCapabilities,SettingsIdentity}` reads only a preview subset: active QSIDs, dynamic entry counts, explicit supported keycodes, full settings identity and transitions are not represented. This is safe for browsing; it cannot become an authorization contract without strict complete validation and tests. Complete plan 3a before enabling beta settings.
2. **Profile selection changes only a catalog preview** (AKW-015, 024, 060, 085). **Release blocker for nine-profile offline support; offline implementation.** `src/ui/ak820_beta1_profiles.rs::select_preview_profile` changes its local `SelectorState`; it does not construct an editable project. `src/app_init.rs::new_ak820_demo` constructs the fixed alpha-style example and disables Mouse Keys, Auto Shift and Tap Dance. Catalog tests cover module labels, descriptions, navigation and local selection, not nine editable profile models. Implement offline project selection and source/context tests for every enabled module.
3. **Schema03 behavior is not adapted to AK820** (AKW-024, 045). **Release blocker for schema03 editing; offline implementation.** The AK820 whitelist rejects unsupported extension/QMK commands, and connection reads require zero Tap Dance/Key Override capacities. Generic inherited editors do not qualify AK820 row ranges, split-page storage, CRC, defaults, active QSIDs, ACK/getter/full-NVM verification or preservation of neighboring bytes. Add firmware parity fixtures and fault cases for each typed codec/setter; do not expose controls from reserved storage.
4. **Complete backup and migration are missing** (AKW-021, 040–045). **Release blocker for complete backup/restore; offline implementation.** `src/entlayout.rs::import_entlayout_from_path` explicitly blocks AK820 import. Existing export is a partial editor snapshot, as `src/ak820_help.rs` explains. The firmware backup formats, complete typed data, explicit image-pair transitions, pre-import/reset safety copies, undo import and restore history are not implemented for AK820. Existing generic `.entlayout` tests do not establish those contracts. Complete plan 3b before claiming settings recovery.
5. **Companion firmware installation and OEM recovery are missing** (AKW-030–034, 043–044, 050–054, 060, 083). **Release blocker for installer replacement; offline implementation before hardware acceptance.** The preview cannot select and validate a flash operation; no AK820 packer parity or installer/rollback state machine is connected. Existing generic firmware/update modules and catalog hashes do not prove image preparation, protected regions, ownership, confirmation, cancellation or installed-image verification. Implement plan 4a offline before requesting hardware qualification. Keep standalone installers.
6. **Positive full verification is not covered end to end** (AKW-081–082, 085). **Release blocker for complete verification coverage; offline fixture work.** `src/hid_ak820_tests.rs::full_verification_rejects_zero_code_trial_and_unknown_manifest_hash` checks negative identity cases. `src/ui/ak820_connection_tests.rs::complete_verified_connection_reads_actual_definition_and_all_settings` starts with `test_verified_ak820_device` and invokes `load_verified_ak820`, bypassing real image verification. It does check both encoder mappings across six layers. Add an approved exact-image positive fixture through `load_ak820`, then test complete reads and failures. A fabricated image must not be reported as verification of a released image.
7. **Desktop packages and target behavior need evidence** (AKW-060, 083–085). **Release blocker per claimed OS/CPU target; offline packaging plus hardware USB acceptance.** `.github/workflows/desktop-dev.yml` defines all six OS/CPU builds and SHA256 files; Linux jobs run host tests. It publishes raw development binaries. A workflow definition does not establish successful CI, platform execution, minimum OS versions, package dependencies, USB operation, startup/memory use, signing or notarization. Required target qualification remains open; the fresh host suite does not prove six-target builds or platform runtime behavior.
8. **Broader product functions remain open** (AKW-021–022, 061–064, 070–072). **Offline implementation gaps for the corresponding product scope; helper acceptance is a separate later stage.** The scoped readback path and bundled RU/EN help are present, but complete backup-protected reset, settings-import undo, per-control accessible help, the AK820 application updater, optional layout/LED helper and a sanitized downloadable operation report are not established by this implementation. `src/diagnostics.rs` supplies local logging; it is not the specified redacted report. Prove cross-instance/helper ownership separately from a session mutex. No exhaustive privacy/network audit or cross-process ownership qualification is claimed here.

These are unfinished requirements, not evidence that the existing read-only rejection should be weakened. None requires a device write to implement codecs, offline UI, parsers, policy or operation models.

## Acceptance decision

**Architecture acceptance of the implementation is incomplete.** The refined plan is actionable, but the current source implements a bounded alpha.3 editor plus beta.1 catalog browsing. First close offline contracts/editors and backups (3a/3b), then packer/operation models (4a), then target packaging (4b). Record fresh tests and independent review for the exact resulting tree. Hardware-only acceptance remains separate: USB identity/access, fresh unlock, safe loader/write/readback, physical keys/encoder, retention and OEM rollback. No commit, push or device-operation approval is implied.
