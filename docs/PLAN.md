# AK Configurator implementation plan


## Planned issue fixes, unified navigation and MCP completion — 2026-10-28

Planning baseline: `25cceb84567ad5721d056dde160aa22de2c76c7b`; [issues #2–#7](https://github.com/dvino/ak-configurator/issues). This section specifies future work, not completed fixes or authorization for device operations. Recheck the branch, issues and ownership before implementation.

1. **Inventory and integrate existing work.** Preserve the dirty primary checkout and its five local commits. Compare each with the then-current remote: the four modified agent/routing documents; untracked release policy, migration preview/schema modules, UI and schema fixtures. Establish ownership, original intent, overlap and dependencies; preserve unique content, review and test applicable changes in an isolated worktree, and record for each whether already integrated, superseded, adapted or still pending. Never overwrite or silently discard concurrent work.
2. **Shared session and responsiveness (#2, #3, #4, #5).** Trace device identity, connection generation and ownership across GUI, helper, RGB, backup and unlock. Represent connected, temporarily busy, disconnected and unsupported separately; keep pages and version stable while ownership changes. Move blocking HID work off the UI thread, bound waits and cancellation, invalidate stale results and keep close usable. Reproduce the reported flicker, RGB hang and unlock failure before assigning causes; capture safe diagnostics and add targeted fault/timeout/reconnect tests. Explain unlock's physical action and progress, completion, timeout and rejection. After an ambiguous write, stop without blind retry or automatic restore.
3. **Backup and restore (#2).** Make read, save, select backup, compatibility preview and restore understandable in one page. Diagnose exact-image recognition and ownership before changing admission. Show exact source/target and specific blocked reason; an old backup is not assumed compatible. Restore remains blocked until exact reviewed image, explicit allowed transition, complete safety snapshot and readback requirements are met. A read-only snapshot must not imply write support for beta.4.
4. **One navigation, no application modals (#6).** Replace menus and utility/modal windows with a consistent persistent main-window navigation for all functionality: editor, firmware, backups, application settings and help. Preserve editor state across pages, provide Back/Cancel and inline confirmations/progress, responsive narrow-window layouts, keyboard accessibility and coherent RU/EN labels. Native file selection must not block the app: use a non-modal path-entry/file-browser flow where OS dialogs cannot meet that requirement. Help alone may be a separate non-modal window. Remove the separate firmware-profile navigation item; put profile descriptions in help, linked contextually from firmware. Remove duplicate settings entries and ambiguous inherited labels.
5. **Straightforward installation.** Show the already connected eligible keyboard by default; if several match, ask for a choice, and if none or identity is uncertain, show why. Pin the selected device and generation; revalidate before irreversible steps and do not silently switch after reconnect. Present current and target release, one clear primary action, concise consequences and a link to profile help; keep beta.3 an explicitly labelled alternate where supported. Offer an explicit checkbox to proceed without saving an OEM backup, with a clear warning that stock recovery cannot be relied on without a verified compatible copy. Distinguish optional saving of a new OEM archive from required device-specific reads, safe image preparation and update/settings safety capture. Absence of a newly saved archive alone must not block; if the exact source-to-target preparation requires existing OEM recovery bytes, missing required inputs, failed reads or preparation block with a specific reason. Keep exact image and transition admission, physical confirmation, one flash attempt and verification; never present unsupported settings writes as available.
6. **Indicator status (#7).** Separate observed OS layout from the configured LED mapping, explain On/Off/breathing and show paused/busy/unknown without modifying saved choices. Test mappings and stable refresh offline; physical LED behavior requires separately authorized observation and must be reported separately.
7. **Wayland.** Investigate native window lifecycle, startup, clipboard/file access, scaling and tray on real Wayland sessions and supported compositors, alongside X11 regression. The current Wayland fallback keeps the window visible; retain a recoverable visible window until native hide/restore and real tray-host loss/recovery are demonstrated. Headless Weston and synthetic tray checks do not establish real desktop behavior. Document unsupported compositor/host cases and actual platform evidence.
8. **Complete MCP.** Use [MCP_IMPLEMENTATION_PLAN.md](MCP_IMPLEMENTATION_PLAN.md) as the detailed inventory, reconcile it against current code and update it as stages land. Finish P0 positive packed-image bootstrap, strict replay/failure/cancellation, bounded reports, helper/session ownership and Windows stdio plus independent client interoperability; then P1 shared typed settings, backup/restore and functional test contracts; then P2 protected update and explicitly scoped hardware diagnostics. Reuse the GUI's services and exact-image policy, keep read-only default, bounded operations, local private artifacts, fail-stop and explicit operation-specific authorization. Planned tools are not present until implemented and verified; MCP does not control an existing GUI merely because native UI smoke exists.
9. **Acceptance and delivery.** For every issue record reproduction, root cause, fix and negative-path regression; use offline models and headless UI tests for deterministic cases, then native Windows/Linux and real Wayland checks. Cover no/single/multiple devices, reconnect, busy, unsupported images, optional OEM archive, failed required reads, cancellation and close. Hardware RGB/unlock/restore/flash requires fresh authorization for the exact operation; report source, offline, platform and physical results separately. Review each bounded change independently, update EN/RU help and status, then run appropriate checks. This planning-only commit uses `[skip ci]`; later implementation checks and CI require their own delivery decision.

Beta.4.1 uses release defaults and the existing fresh backup, confirmation, one-attempt loader and full readback gates. Saved-settings writes and restore remain blocked. Use beta.4.1 as the default installation target and retain beta.3 as an explicit alternate. Beta.4.1 flashing uses only its exact pinned catalog and image bindings; do not infer authorization from beta.4 profile flags. Keep hardware validation false and settings writes/restore blocked. Offline project import undo preserves unrelated subsequent profile edits; nonregular imports are rejected. File reads and atomic writes run in the dialog worker; native dialog and slow-filesystem behavior still need platform checks.

This plan tracks the agreed [requirements](REQUIREMENTS.md) for `dvino/ak-configurator`; firmware remains in `dvino/ak820`. Source implementation and offline verification do not authorize live keyboard operations or establish physical behavior.
