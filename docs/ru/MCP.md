# Диагностика через MCP

Это первая, **частичная реализация P0** из [плана интеграции](MCP_IMPLEMENTATION_PLAN.md). Она включается отдельно, работает только на чтение и отсутствует в обычных сборках. Это не завершённая приёмка P0 и не подтверждение готовности альфа-релиза. Версия приложения остаётся `0.1.0-alpha.1`. Фактически проверенные исходники и платформы указаны в [REVIEW.md](REVIEW.md).

## Сборка и подключение

Соберите эти исходники с закреплённым lockfile:

```sh
cargo build --locked --release --features mcp
```

Укажите локальному MCP-клиенту исполняемый файл `target/release/ak-configurator` в Linux или `target/release/ak-configurator.exe` в Windows и аргументы:

```json
["--mcp-stdio", "--mcp-access=read-only"]
```

Используйте абсолютный путь. Процесс обменивается MCP через унаследованные stdin/stdout с официальным SDK `rmcp = 3.8.0`. Для запуска не нужны GUI или дисплей; сетевого слушателя MCP нет. Согласование протокола и получение списка инструментов/ресурсов не перечисляют USB и не открывают клавиатуру. При компоновке сохраняются существующие зависимости GUI. Обычные пакеты собираются без `mcp` и отклоняют запуск MCP; эту версию нужно собрать явно.

Прежде чем открывать ту же клавиатуру через MCP, закройте соединение GUI или фонового помощника. Существующая кооперативная блокировка устройства сохранена; MCP не отбирает владение. Занятое или недоступное устройство возвращает ошибку. Сторонние программы могут не соблюдать блокировку приложения.

## Доступные инструменты

| Инструмент | Действия сейчас | Обращение к устройству |
| --- | --- | --- |
| `ak820_devices` | Список кандидатов; `refresh` обновляет перечисление | Только перечисление USB; кандидат ещё не означает распознанный образ |
| `ak820_session` | `open` с `load: "diagnostics"`, сохранённый `status`, `close` | Явное исключительное владение и диагностическая инициализация; без загрузки настроек |
| `ak820_read` | `identity`, `capabilities`, `storage`, `connection` | Identity/capabilities берутся из сохранённых данных; storage/connection выполняют типизированное чтение FD01 |
| `ak820_tests` | `list`, `run` для `protocol.smoke`; у mock также `protocol.errors` | Ограниченное диагностическое чтение или синтетические проверки ошибок; без setter-команд |
| `ak820_trace` | `start`, `status`, `stop`, только metadata | Метаданные обмена через существующий транспорт только для чтения |
| `ak820_operation` | `status`, `cancel` | Проверка состояния или запрос кооперативной отмены асинхронного открытия |

Схемы аргументов закрыты. Нет инструмента для произвольной HID-команды, адреса памяти, shell, пути, unlock, изменения настроек, сброса, загрузчика или прошивки. Политика HID только для чтения необратима в пределах процесса. Успешный ответ или `protocol.smoke` не подтверждает работу физических клавиш, энкодера, светодиодов или сохранение настроек.

## Последовательность диагностики

1. Вызовите `ak820_devices` с `{"refresh":true}` и выберите возвращённый непрозрачный `device_id`. Не конструируйте его из USB-пути.
2. Вызовите `ak820_session` с `{"action":"open","device_id":"RETURNED_ID","load":"diagnostics"}`. Ответ `accepted` содержит `data.operation_id` и ещё не означает успешное распознавание.
3. Опрашивайте `ak820_operation` с `{"action":"status","operation_id":"RETURNED_OPERATION"}`. После завершения проверьте `data.state` и вложенный результат `data.result`. Возьмите `device_session_id` из успешного вложенного результата. При ошибке состояния хранилища может сохраниться остановленный сеанс для просмотра сохранённых данных и явного закрытия.
4. Читайте фиксированные разделы или запускайте `protocol.smoke` с этим ID. Сейчас smoke читает диагностический статус и явно помечает физические проверки `SKIP`.
5. Явно закройте сеанс. ID принадлежат этому процессу и устаревают после закрытия или нового запуска; это не пути файловой системы.

Для настоящей клавиатуры инициализация читает манифест и весь упакованный CODE ограниченными запросами FD00 и сверяет точный встроенный контракт образа. Только распознанные образы beta.3 допускаются к FD01 и последующим обычным getter-командам протокола/UID. FD01 проверяется до этих getter-команд и после них. Dirty/batch/unlock, fault, неверный ответ, тайм-аут или отключение останавливают сеанс без предположительных последующих команд и автоматического повтора. Диагностика не отмечает настройки готовыми. Обычная проверка прошивки в GUI теперь тоже распознаёт CODE перед getter-командами.

Есть один владелец, одна операция с устройством одновременно и ограниченная очередь рабочего потока. Распознавание CODE имеет срок 120 секунд с проверкой отмены между пакетами; отдельный обмен сохраняет существующий тайм-аут транспорта. Состояние операции показывает крупные этапы, но не прогресс по байтам. Стандартная отмена MCP-запроса отсоединяет его ответ и **не** отменяет чужую работу потока. Для отмены асинхронного открытия используйте `ak820_operation.cancel`. EOF запрашивает отмену и ожидает завершения потока/помощника. Владение не освобождается только потому, что клиент перестал ждать.

## Отчёты и трассировка

Результаты инструментов используют `ak820-mcp-result-1` в `structuredContent` с текстовым вариантом от SDK. Они содержат метки backend/evidence, доступную идентификацию образа/сеанса, границы проверки и структурированные ошибки. Принятую операцию нужно довести до конечного результата. Ошибки инструментов выставляют `isError`; физическое поведение всегда помечено непроверенным.

Ресурсы: `ak820://server`, встроенный публичный каталог `ak820://catalog/<hash>`, пустые зарегистрированные входы `ak820://inputs` и последние smoke-отчёты `ak820://report/<id>`. В памяти хранятся до 32 smoke-отчётов. Набор ошибок возвращает проверки непосредственно. Эта версия не пишет отчёты по произвольному пользовательскому пути; клиент может сам сохранить полученный JSON.

Трассировка требует открытого сеанса и `mode: "metadata"`. Пределы — 8 МиБ и 60 секунд. Start возвращает непрозрачный ID и ресурс страницы вида `ak820://trace/<id>/page/0`. На странице не более 128 записей: семейство команды, число байтов, время и результат транспорта. Содержимое запросов/ответов, адрес памяти, USB-путь и серийный номер не экспортируются. Трассу нельзя воспроизвести. Хранится только последняя трасса в памяти процесса; новая заменяет остановленную/истёкшую. Завершение процесса удаляет отчёты и трассы. Сама инициализация не попадает в трассу, поскольку запись начинается после открытия сеанса.

## Офлайн-разработка и проверка настоящего окна

```sh
cargo test --locked --features mcp-mock --bin ak-configurator -- --test-threads=1
cargo build --locked --features mcp-mock
python3 scripts/test_mcp_stdio.py --binary target/debug/ak-configurator
dbus-run-session -- xvfb-run -a env AK820_RUNTIME_SMOKE_TRAY_FIXTURE=1 \
  python3 scripts/test_ak820_runtime_smoke.py \
  --binary target/debug/ak-configurator --report target/runtime-smoke-linux.json
```

В Windows используйте `python` и путь с `.exe`. В Windows и macOS запускайте runtime-скрипт без `dbus-run-session` и `xvfb-run`. `mcp-mock` предназначен только для разработки и не должен попадать в поставляемые пакеты. Его строгие сценарии FD01 проверяют разбор ответов/ошибок и помечены `host_model`; успешную полную инициализацию по упакованному CODE они не имитируют. Проверка подпроцесса охватывает версии `2025-11-25` и `2026-07-28`, шесть инструментов, ресурсы, ошибки, ограничение сообщений и EOF. Это локальный протокольный клиент, а не сертификация MCP Inspector или сторонних клиентов.

`--runtime-smoke` запускает настоящий нативный renderer приложения с офлайн-моделью и новыми временными настройками. Проверяются запуск окна, переходы на RGB/настройки приложения и продолжение отрисовки. Отчёт также содержит время от входа в процесс до создания окна, заставки, инициализации редактора и его первого кадра; harness и условие выпуска отклоняют отсутствие или неверный порядок этих этапов. Это время передачи кадров на отрисовку, не измерение фактического показа системой. Все три семейства ОС создают рабочий трей, скрывают/восстанавливают нативное окно и проверяют его видимость/отрисовку. В Linux изолированная фикстура выступает синтетическим StatusNotifier-host, проверяет экспорт значка/меню, вызывает рабочую активацию через D-Bus, затем исчезает для проверки автоматического восстановления окна. Она не рисует панель рабочего стола. Настоящему Linux-окружению нужен совместимый StatusNotifier-host; при его отсутствии/потере окно остаётся или становится видимым. Физический щелчок по трею, работа живого OS-помощника, задержка HID и прошивка не проверяются. Linux Xvfb подтверждает X11, но не Wayland. `--demo-ak820` использует ту же изоляцию. Оба режима запрещают смешивание режимов запуска и блокируют рабочие входы к оборудованию, автозапуску, захвату, обновлениям и системной интеграции. Это изоляция на уровне приложения, а не системная песочница или утверждение о безопасности каждого унаследованного/игнорируемого теста на личной учётной записи.

CI запускает GUI smoke для всех шести кандидатов Linux/Windows/macOS и связывает отчёт с SHA256 упакованного исполняемого файла. Проверка релиза требует эти отчёты. Настройка такого условия не означает, что новые Windows/macOS-файлы уже запускались; фактические результаты указаны в [REVIEW.md](REVIEW.md).

## Что ещё предстоит

Остаются положительная фикстура полной инициализации по упакованному образу, проверка живого владения/отмены/ошибок помощника, более полные отчёты и трассировки, фактическое выполнение Windows MCP/GUI и физические измерения задержки/светодиодов. Загрузка/редактирование настроек, резервные копии, обратимые функциональные наборы, управление/наблюдение OS-индикатора и защищённые обновления относятся к следующим работам плана. MCP-процесс не управляет уже запущенным GUI. Жизненный цикл окна проверяет отдельный нативный smoke-runner. Текущая версия позволяет разрабатывать агентную диагностику и повторять ошибки на host-модели, сохраняя явный список незакрытых условий приёмки.
